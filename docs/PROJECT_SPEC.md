## 0. 이 문서를 읽는 AI 에이전트에게

- 이 문서는 **풀스코프 명세**다. 모든 기능이 1차 릴리즈 대상은 아니다.
- 각 기능에는 우선순위 태그가 붙어 있다: **`P0`** (1차 릴리즈 필수) / **`P1`** (2차) / **`P2`** (이후)
- 구현 순서는 §13 로드맵을 따른다. 마일스톤을 건너뛰지 말 것.
- §5(알고리즘), §7(평판), §8(어뷰징 방지), §6(데이터 모델)은 **이 서비스의 핵심 자산**이다. 임의로 단순화하지 말고, 변경이 필요하면 먼저 질문할 것.

### 불변 원칙 (violate 금지)

1. **`votes` 테이블은 append-only.** 어떤 경우에도 UPDATE/DELETE 하지 않는다. 무효 처리는 `is_valid` 플래그로만 한다. (§5.6)
2. **ELO 계산은 Postgres RPC 함수 내부에서만 수행한다.** 클라이언트가 점수를 계산해 전송하는 구조 금지. (§9.3)
3. **매치업 쌍은 서버가 생성한다.** 클라이언트가 임의 쌍을 제출할 수 없다. (§8.2)
4. **알고리즘 임계값·가중치를 코드에 하드코딩하지 않는다.** 전부 `app_config` 테이블에서 읽는다. (§5.5)
5. **투표는 타 유저에게 항상 익명이다.** 유저가 명시적으로 공개한 "선택 이유"만 닉네임과 함께 노출된다. (§4.1.2)

## 1. 서비스 정의

### 1.1 한 줄 정의

수험생들이 **(대학, 학과) 조합 두 개를 1:1로 비교 투표**하고, 그 결과를 누적해 **정량화된 "수험생 선호도 지수"** 를 만드는 커뮤니티.

### 1.2 투표 질문 (서비스의 헌법)

> **"당신이 이 두 곳을 모두 갈 수 있다면, 어디를 선택하시겠습니까?"**

이 문구는 서비스 전체에서 일관되게 사용한다. "어디가 더 좋은 학교인가"가 아니라 **"당신이라면 어디를 가겠는가"** 이며, 이 차이가 서비스의 정체성이다. UI 카피, 공유 이미지, 약관 어디에서도 전자로 바꾸어 표현하지 않는다.

### 1.3 문제의식

수험생이 대학을 고를 때 참고할 수 있는 정량 지표는 이미 많다 — 입결(백분위·등급컷), 취업률, 등록금, 재학생 수, 장학 규모. 대학알리미·대학어디가 등이 이를 제공한다.

그러나 실제 선택에서 매우 큰 비중을 차지하는 **"수험생 선호도"** 는 어디에도 수치화되어 있지 않다. 이는 학교 위치, 브랜드 이미지, 대학가 상권, 통학 여건, 또래 인식 등 정량화되지 않은 요소들의 총합이며, 현재는 커뮤니티의 감(感)과 학교별 옹호 문화(소위 "훌리건")에 의해 왜곡된 형태로만 유통된다.

**이 서비스는 그 선호도를 집단 투표로 측정해 하나의 숫자로 만든다.**

### 1.4 비(非)목표 — 명시적으로 하지 않는 것

- 대학의 교육 품질, 학문적 수준, 연구 역량 평가
- 입결(합격 점수) 예측 또는 대체
- 진학 상담 / 입시 컨설팅

이 세 가지는 랭킹표 고지 문구에도 명시한다. (§12.1)

### 1.5 공개 페이지화 `P1`

§1.2 ~ §1.4 의 내용과 §8.6(산출 방식 공개)을 묶어 **"이 서비스를 만든 이유"** 정적 페이지로 공개한다. 지표가 신뢰받으려면 의도와 계산 과정이 모두 공개되어 있어야 한다. 랭킹표 하단과 푸터에서 상시 접근 가능하게 한다.

## 4. 기능 명세 — 투표 & 랭킹

### 4.1 매치업 투표 `P0`

**화면 구성**
- 좌우 2분할 카드 (모바일: 상하 분할). 각 카드에 대학명, 학과명, 대학 로고, 지역 배지
- 하단 고정 문구: "당신이 이 두 곳을 모두 갈 수 있다면, 어디를 선택하시겠습니까?"
- 카드 선택 → 즉시 확정 → 결과 오버레이(양쪽 득표율, 내 선택이 다수/소수인지) → 다음 매치업 자동 로드
- "잘 모르겠음 / 건너뛰기" 제공. 스킵은 투표로 기록되지 않으나 `skips` 에 남긴다 (매칭 품질 지표)

**매치업 생성 규칙**
- 매치업 쌍은 반드시 서버가 결정하고 토큰을 발급한다 (§8.2)
- 좌/우 배치는 매 요청마다 랜덤화 (위치 편향 제거)
- 유저가 이미 투표한 쌍은 재출제하지 않는다

#### 4.1.1 선택 이유 작성 `P0`

- 투표 직후 선택적으로 한 줄 이유를 입력할 수 있다 (최대 200자)
- **작성을 강제하지 않는다.** 강제하면 투표 표본이 급감한다. 대신 작성된 이유를 상세 페이지·스레드에 우선 노출해 유도한다
- 작성 시 **공개 여부를 선택**한다 (기본값: 공개). 공개된 이유는 닉네임과 함께 노출되고 §7 평판의 대상이 된다

#### 4.1.2 익명 정책 (중요)

**투표 자체는 타 유저에게 항상 익명이다.** 어떤 화면에서도 "누가 어느 쪽을 골랐는지"는 노출되지 않는다.

- 서버(DB)는 `votes.profile_id` 를 보유한다. 어뷰징 추적과 중복 방지에 필수이므로 완전 익명은 채택하지 않는다
- 타 유저에게 노출되는 것은 오직 **유저가 공개 선택한 "선택 이유"** 뿐이다
- 프로필의 투표 기록 역시 공개된 이유만 표시한다 (§6.2)

**설계 근거**: 실명 노출 시 투표는 사회적으로 안전한 방향으로 편향된다. 같은 학교 친구나 커뮤니티 이용자가 볼 수 있다는 인식은 솔직한 선택을 억제하며, 그 순간 이 지표는 "선호도"가 아니라 "공개적으로 표명 가능한 선호도"를 측정하게 된다. 또한 실명 노출은 특정 선택을 한 유저에 대한 보복(브리게이딩)의 통로가 된다.

**추가 모드** `P2`
- 이상형 월드컵 모드: 16강/32강 토너먼트. 결과 공유 이미지 생성. 유입용 바이럴 기능
- 특정 Program 지목 대결: "고려대 컴퓨터학과의 라이벌 찾기"

### 4.2 랭킹표 (핵심 화면) `P0`

**메타포**: 입결표. 수험생에게 이미 익숙한 밀도 높은 표 형식.

**표시 항목**

| 컬럼 | 모바일 | 데스크톱 |
|---|---|---|
| 순위 | ● | ● |
| 변동 (▲3 / ▼1 / —) | ● | ● |
| 대학 (로고 + 명칭) | ● | ● |
| 학과 | ● | ● |
| **선호도 지수** | ● | ● |
| 계열 배지 | 축약 | ● |
| 지역 배지 | 생략 | ● |
| 표본 수 | 생략 | ● |
| 신뢰도 배지 | ● | ● |
| 승률 | 생략 | ● |

모바일은 핵심 5개 컬럼만, 행 탭 시 확장. 데스크톱은 전 컬럼 표시. (§10.2)

**필터 / 정렬**
- 계열 필터 (기본값: 전체, **UI에서 눈에 띄게 배치**)
- 지역 필터 (서울 / 수도권 / 광역시 / 그 외)
- 대학 검색, 학과 검색
- 즐겨찾기 상단 고정 `P1`

#### 4.2.1 계열 간 비교 안내 (필수)

랭킹표에 상시 노출되는 안내 문구:

> 계열이 다른 학과 사이의 점수 차이는 참고용입니다. 응답자의 계열 분포에 영향을 받기 때문에, 정확한 비교는 **같은 계열 안에서** 이루어질 때 가장 신뢰할 수 있습니다.

**근거**: 매칭의 대부분이 동일 계열 내에서 이루어지므로 계열 내 순위는 안정적이다. 그러나 계열 간 점수 눈금을 이어주는 것은 소수의 교차 계열 매치이고, 이 결과는 응답자 집단의 문·이과 비율에 좌우된다. 구조적 한계이며 숨기지 않고 명시한다.

#### 4.2.2 신뢰도 배지

임계값은 `app_config` 에서 읽는다. 런칭 직후에는 표본이 적으므로 낮은 프리셋으로 시작해 데이터 축적에 따라 상향한다.

| | **런칭 프리셋** (기본) | **성숙 프리셋** |
|---|---|---|
| `잠정` (점수 회색, 순위 미부여) | n < 10 | n < 30 |
| `표본 부족` (주황 점) | 10 ≤ n < 40 | 30 ≤ n < 200 |
| 정상 (배지 없음) | n ≥ 40 | n ≥ 200 |

- 프리셋 전환은 **전체 누적 투표 수 50,000** 도달 시 검토하되, 자동 전환하지 않고 운영자가 판단해 `app_config` 값을 변경한다
- `잠정` Program은 기본 랭킹표 하단 별도 섹션으로 분리한다

#### 4.2.3 티어 밴딩 `P1`

점수 구간을 티어로 묶어 색상 밴딩. 입결표의 "라인" 감각을 재현하며, 미세한 점수 차이에 과몰입하는 것을 완화하는 효과도 있다.

## 5. 선호도 지수 알고리즘

### 5.1 채택 방식: ELO

**1차 릴리즈는 ELO 실시간 갱신 방식으로 구현한다.**

```
E_a = 1 / (1 + 10^((R_b - R_a) / 400))
R_a' = R_a + K_eff × (S_a - E_a)
R_b' = R_b + K_eff × (S_b - E_b)
```
- `S_a` = 1 (승) 또는 0 (패). 무승부 없음
- 초기 점수: **1500** (모든 Program 동일)
- 입결 등 외부 지표로 초기값을 시드하지 **않는다**. 시드하면 결과가 "입결 순위의 재생산"이라는 비판을 피할 수 없고, 서비스의 존재 이유와 충돌한다

### 5.2 실효 K값

```
K_eff = K_base(n) × w_age × c_trust × r_reputation
```

**K_base — 적응형** (`app_config` 에서 읽는다)

| 해당 Program 누적 투표 수 `n` | **런칭 프리셋** | **성숙 프리셋** |
|---|---|---|
| 1단계 | n < 10 → **48** | n < 30 → 40 |
| 2단계 | 10 ≤ n < 40 → **32** | 30 ≤ n < 100 → 24 |
| 3단계 | n ≥ 40 → **24** | n ≥ 100 → 16 |

> 런칭 초기에는 어차피 표본이 없으므로 임계를 낮게 잡고 K를 크게 두어 빠르게 자리를 잡게 한다. 표본이 쌓인 뒤 임계와 K를 함께 조여 안정화한다.

> 두 Program의 `n`이 다를 경우, **각자의 K_base를 각자에게 적용**한다. 제로섬이 깨지지만, 신규 Program의 빠른 수렴이 총점 보존보다 중요하다.

### 5.3 연령 가중치 `w_age`

만 18세 이하는 1.0, 만 19세부터 0.5에서 시작해 연령이 오를수록 선형 체감한다.

```
age ≤ 18                        → w_age = 1.0
age ≥ 19                        → w_age = max(0.10, 0.50 - 0.04 × (age - 19))
```

| 만 나이 | 18↓ | 19 | 20 | 21 | 22 | 24 | 26 | 29↑ |
|---|---|---|---|---|---|---|---|---|
| w_age | 1.00 | 0.50 | 0.46 | 0.42 | 0.38 | 0.30 | 0.22 | 0.10 |

**N수생 보정**: 프로필 `status = 'N수'` 인 경우 `w_age + 0.30` (상한 1.0). 만 19~21세 재수·삼수생은 실제 수험 당사자이므로 보정이 필요하다.
- 단 자기신고 값이므로 남용 방지 장치를 둔다: 만 23세 이상은 보정 미적용, `status` 변경은 이력 기록(§6.2), 변경 후 7일간 보정 미적용
- 비로그인 투표는 `w_age = 0` (기록만 남기고 지수 미반영)
- 계수(0.50 / 0.04 / 0.10 / N수 보정치)는 전부 `app_config` 값이다

### 5.4 매칭 큐 정책

```
1) 계열 선택
   - 90% : 동일 계열 내 매칭
   - 10% : 교차 계열 매칭   ← 계열 간 점수 눈금을 이어주는 역할

2) 계열이 정해지면, 그 안에서 쌍 선택
   - 70% : ELO 차이 ≤ 200 인 근접 쌍   (정보량 최대화)
   - 30% : 투표 수 하위 20% Program 우선 포함   (노출 형평성 / 탐색)

3) 필터
   - 해당 유저가 이미 투표한 쌍 제외
   - 비활성(is_active = false) Program 제외
   - 좌/우 랜덤 배치
```

- 모든 비율은 `app_config` 파라미터로 구현한다. 하드코딩 금지
- **콜드스타트 구간(전체 투표 수 < 5,000)에서는 근접 쌍 비율을 30%로 낮추고 무작위 비중을 높인다.** 초기에는 ELO 추정치 자체가 부정확해 "근접"이 의미 없기 때문
- 유저 프로필 계열을 매칭에 반영하면 응답 품질은 오르나 데이터가 편중된다. **초기에는 반영하지 않고**, 데이터 축적 후 A/B로 검증한다

### 5.7 향후 확장: Bradley-Terry 배치 재적합 `P2`

ELO는 표가 들어오는 **순서에 따라 최종 점수가 달라지고**(경로 의존성), 표본이 적은 Program의 불확실성을 표현하지 못한다. 이를 해소하려면 전체 투표 로그를 한 번에 놓고 최대우도추정하는 Bradley-Terry 모델로 전환하면 된다 (ELO는 이 모델의 온라인 근사판이다). MM 알고리즘 기준 수천 개 항목도 수 초 내 수렴한다.

**지금 구현하지 않는다. 다만 아래 두 원칙을 반드시 지켜 전환 가능성을 열어둔다:**

1. **`votes` 는 append-only.** 무효 처리는 `is_valid = false` 로만 한다
2. 각 투표에 **당시 적용된 가중치(`weight_applied`)와 타임스탬프**를 저장한다

이 두 가지만 지키면 언제든 전체 재계산이 가능하다.

## 7. 유저 평판 시스템 `P1`

### 7.1 구조

- 유저가 공개한 **선택 이유**에 다른 유저가 추천 / 비추천할 수 있다
- 누적 결과로 유저의 평판 점수가 산출되고, 이것이 투표 가중치에 **제한적으로** 반영된다

```
raw_rep(u)   = Σ(공개 이유의 추천) - Σ(공개 이유의 비추천)
r_reputation = clamp(1 + 0.15 × tanh(raw_rep / 50), 0.85, 1.15)
```

| raw_rep | -100 | -50 | -10 | 0 | +10 | +50 | +100 |
|---|---|---|---|---|---|---|---|
| r_reputation | 0.86 | 0.89 | 0.97 | 1.00 | 1.03 | 1.11 | 1.14 |

`tanh` 으로 수확 체감을 주고, 상·하한을 ±15%로 묶는다. 상수는 `app_config` 값이다.

### 7.2 왜 영향력을 좁게 묶는가 (설계 근거 — 중요)

평판이 투표 가중치를 크게 좌우하면 **다수 의견에 동조할수록 영향력이 커지는 되먹임 고리**가 생긴다. 소수 선호를 가진 유저는 비추천을 받아 평판이 깎이고 → 가중치가 줄어 → 지표에서 그 선호가 지워진다. 그 결과 이 지표는 다수 의견을 증폭하는 기계가 되며, 애초에 없애려던 편향이 다른 경로로 되돌아온다.

**따라서 평판은 "가중치를 크게 바꾸는 장치"가 아니라 "성실한 참여에 대한 소폭의 보상"으로만 설계한다.**

### 7.3 추천/비추천 대상의 한정 (중요)

**평가 대상은 "어느 학교를 골랐는가"가 아니라 "그 선택의 논거가 설득력 있는가"다.**

이 구분은 §4.1.2의 익명 정책에 의해 구조적으로 강제된다 — 투표 자체가 비공개이므로 공개된 이유(텍스트)만 평가 대상이 될 수 있다. 이유를 작성하지 않은 유저는 평판이 형성되지 않으며, `r_reputation = 1.0` 으로 중립 유지된다.

### 7.4 평판 시스템 자체의 어뷰징 방어

평판 시스템은 그 자체가 새로운 공격면이다. 아래를 함께 구현한다.

- 동일 유저의 이유에 대한 추천/비추천은 **일 3회까지** (특정 인물 집중 공격 차단)
- 짧은 시간 내 한 유저에게 비추천이 집중되면(예: 10분 내 5건 이상, 서로 다른 계정) 해당 건들을 **보류 처리**하고 어드민 검토 큐로
- 신규 계정(가입 7일 미만)의 추천/비추천은 평판에 미반영
- 비추천 사유가 "논거 품질"이 아니라 "학교 선택"인 경우를 막기 위해, 비추천 시 사유 선택 필수 (근거 없음 / 비방 / 스팸 / 기타)
- `r_reputation` 은 일 배치로 재계산하며 실시간 반영하지 않는다

## 8. 어뷰징 방지 설계

> **이 서비스에서 어뷰징 방지는 부가 기능이 아니라 핵심 기능이다.** 지표가 조작되는 순간 서비스의 존재 이유가 사라진다. "어느 학교 학생들이 더 단합을 잘하는가" 지표가 되어버린다.

### 8.1 진입 장벽 `P0`
- 지수 반영은 **카카오 로그인 필수**. 카카오 계정은 전화번호 기반이라 다계정 양산에 실질적 비용이 든다
- 만 14세 미만 차단
- 계정 생성 후 10분 경과 전 투표는 `c_trust` 를 낮게 적용

### 8.2 서버 권위 `P0`
- **매치업 쌍은 서버가 생성하고 토큰을 발급한다.** 클라이언트는 토큰 + 선택 결과만 제출한다
- 토큰 TTL 10분, 1회용
- **ELO 계산은 Postgres 함수(RPC) 내부 트랜잭션으로 처리**한다
- RLS: `votes` 는 INSERT만 허용, 본인 행 SELECT만 허용. 타 유저의 `votes` 행은 어떤 경로로도 조회 불가

### 8.3 통계적 편향 탐지 `P1`

**몰표보다 위험한 것은 "일관된 편향 계정"이다.** 특정 대학이 등장할 때마다 항상 그쪽을 선택하는 계정은, 개별 투표만 보면 정상이지만 누적되면 지표를 왜곡한다.

```
유저 u, 대학 U 에 대해:
  personal_rate  = u가 U를 선택한 비율 (U가 등장한 매치업 중)
  global_rate    = 전체 유저가 U를 선택한 비율 (동일 상대 분포 보정)
  deviation(u,U) = personal_rate - global_rate

bias_score(u) = max over U of deviation(u,U)   -- 표본 30 이상인 U만 대상
```

- 임계 초과 시 `c_trust` 를 단계적 감쇠 (1.0 → 0.7 → 0.4 → 0.1)
- **즉시 차단하지 않는다.** 실제로 특정 대학을 선호하는 정상 유저와 구분이 어렵기 때문. 감쇠로 영향력만 줄인다
- 이미 반영된 과거 투표는 소급 조정하지 않는다 (로그는 보존되므로 필요 시 배치 재계산으로 처리 가능)

### 8.4 행동 기반 필터 `P1`
- Rate limit: 시간당 60표 / 일 300표 (`app_config`)
- 응답 시간 필터: `response_ms < 700` 인 투표가 연속 발생하면 자동 검토 큐로
- 동일 IP 다계정 탐지 (보조 신호로만. 학교·PC방 공유 IP 오탐 주의)
- 신규 가입 급증 + 특정 대학 편향 동시 발생 시 어드민 알림

### 8.5 어드민 모니터링 `P1`
- 일별 대학별 승률 추이 — 급변 감지
- 유저별 편향 스코어 분포
- 시간당 투표량 이상치
- 평판 비추천 집중 발생 알림

### 8.6 투명성 `P1`
- 각 Program 상세에 표본 수를 항상 노출
- **"지수 산출 방식" 공개 페이지** — ELO 공식, 연령 가중치 표, 평판 반영 범위, 매칭 정책을 그대로 공개
- §1.5 "만든 이유" 페이지와 함께 푸터에 상시 노출
- 지표가 신뢰받으려면 계산 과정이 감춰져 있으면 안 된다

- 이의제기 채널(문의 메일) 명시
- 특정 대학·학과 비하 표현에 대한 커뮤니티 가이드라인 및 신고 기능 (§12.3)
- §1.5 "만든 이유" + §8.6 "산출 방식" 공개 페이지 — 자의적 조작이 없음을 보이는 근거

### 12.2 개인정보 / 법령
- 만 14세 미만 가입 차단 (개인정보보호법)
- **이용약관 · 개인정보처리방침 필수** — 카카오 로그인 심사 통과 요건이기도 하다

### 13.2 Supabase + Vercel을 유지하는 이유

1. **Postgres가 이 문제에 정확히 맞다.** 랭킹 집계, materialized view, 트랜잭션 내 원자적 ELO 갱신, `pg_cron` 배치, 윈도우 함수 순위 계산 — 전부 Postgres 기본기로 해결된다
2. **RLS로 방어선을 DB 레벨에 둘 수 있다.** 어뷰징 방지가 핵심인 서비스에서 애플리케이션 레이어에만 의존하는 구조는 위험하다. 특히 §4.1.2 익명 정책은 RLS로 강제되어야 한다
3. **이미 손에 익은 스택이다.** 바이브 코딩 사이드 프로젝트에서 학습 비용은 그대로 완주 확률로 직결된다

### 13.3 아키텍처 주의사항

**투표 처리 — Postgres RPC**
```
vote_submit(token, winner_id, reason, reason_public):
  1. 토큰 검증 (존재/미소비/미만료/본인)
  2. 중복 투표 검사
  3. app_config 파라미터 로드
  4. 유저 w_age, c_trust, r_reputation 조회
  5. 양쪽 현재 ELO 조회 (SELECT ... FOR UPDATE)
  6. K_eff 계산 → 새 ELO 산출
  7. votes INSERT + ratings UPDATE + 토큰 consumed
  → 전부 단일 트랜잭션
```

**캐싱 — 비용 방어의 핵심**

랭킹표는 읽기가 폭발하는 지점이다. **수능·정시 원서 접수 시즌에 트래픽이 수십 배로 튄다**는 것을 전제로 설계한다.

- 랭킹표: materialized view + Next.js ISR (`revalidate: 600`)
- Program 상세: ISR (`revalidate: 300`)
- 게시판 목록: 30초 캐시
- 투표 화면만 동적 (`dynamic = 'force-dynamic'`)

**배치 작업 (`pg_cron`)**
- 일 단위: rating 스냅샷, 순위 변동, `age_years`/`vote_weight` 재계산, `bias_score` 재계산, `reputation_mult` 재계산
- 분 단위: materialized view refresh

**Realtime 미사용**
Supabase Realtime을 랭킹 페이지에 붙이지 않는다. 동시 접속자당 커넥션 비용이 크고 실시간 갱신의 가치가 낮다.

### 13.4 개발 환경
- Windows + VS Code
- **Claude Code 단독 사용** (Claude Desktop 경유). Codex 병행 없음 → `AGENTS.md` 불필요

## 14. 디자인 방향

### 14.1 레퍼런스와 차용 지점

| 레퍼런스 | 차용할 것 | 차용하지 않을 것 |
|---|---|---|
| **오르비** | 수험생 타겟 정보 밀도, 입결표 UI 문법 | 낡은 레이아웃 |
| **에브리타임** | 깔끔한 리스트, 빠른 반응성 | 폐쇄형 구조 |
| **디시인사이드** | 말머리, 고밀도 텍스트 리스트, 가벼운 진입 | 무익명성, 거친 톤 |

### 14.2 반응형 — 모바일 6 : 데스크톱 4

**두 레이아웃을 각각 설계한다.** 모바일 레이아웃을 늘려 데스크톱에 쓰거나, 데스크톱을 줄여 모바일에 쓰지 않는다.

| 화면 | 모바일 | 데스크톱 |
|---|---|---|
| 투표 | 카드 상하 분할, 엄지 도달 범위에 선택 영역 | 카드 좌우 분할, 키보드 단축키(←/→) 지원 |
| 랭킹표 | 핵심 5컬럼, 행 탭 시 확장, 필터는 바텀시트 | 전 컬럼 표시, 좌측 고정 필터 사이드바, 헤더 sticky |
| Program 상세 | 탭 전환 (지표 / 이유 / 전적) | 2단 그리드 동시 표시 |
| 게시판 | 리스트형, 하단 탭 내비 | 리스트 + 우측 사이드바(인기글·실시간 랭킹 요약) |

- 브레이크포인트는 Tailwind 기본값 기준, `lg`(1024px)를 데스크톱 전환점으로 삼는다
- 데스크톱 최대 폭을 제한해 좌우 여백이 과하게 벌어지지 않게 한다

### 14.3 원칙

- **정보 밀도 우선.** 여백 넉넉한 SaaS 스타일은 이 타겟에 맞지 않는다. 본문 기준 13~14px, 좁은 행간, 얇은 구분선
- **shadcn/ui 기본 룩을 그대로 쓰지 않는다.** 헤드리스 동작만 취하고 디자인 토큰(색상·반경·간격·타이포)은 전면 재정의한다. 기본값 그대로면 "커뮤니티"가 아니라 "대시보드"처럼 보인다
- **랭킹표는 표처럼 보여야 한다.** 카드 그리드로 바꾸지 않는다. 입결표의 시각적 신뢰감이 이 화면의 자산이다

### 14.4 컬러

**베이스: 블루 ~ 네이비 계열.**

- 많은 대학과 다수 국내 커뮤니티가 이미 사용하는 색이라, 역설적으로 **특정 학교를 연상시키지 않는 중립색**으로 기능한다. 신뢰감·정보성 인상과도 맞는다
- 주 색상은 순수 파랑보다 **네이비/인디고 계열**로 잡고, 포인트에만 채도 높은 블루를 쓴다
- 무채색 그레이 스케일을 폭넓게 확보한다 (고밀도 표에서 회색 단계가 실질적인 정보 위계를 만든다)

**주의 — 투표 화면의 좌우 카드는 색으로 구분하지 않는다.**
좌/우를 파랑 vs 빨강 등으로 칠하면 특정 학교 상징색을 연상시켜 선택에 영향을 준다. **두 카드는 동일한 중립색으로 두고, 선택한 순간에만 포인트 컬러를 입힌다.**

### 14.5 다크모드
`P1`. 야간 학습 시간대 이용률을 고려하면 우선순위가 낮지 않다.

|---|---|---|
