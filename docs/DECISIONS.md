## D-001 · 서비스 영문명 `whereto`

**일자** 2026-08-07 · **관련** §17

한글명 **어디갈래** 확정(§17 후보 중), 영문명·코드 슬러그는 **`whereto`**. 저장소·패키지·도메인 전부 동일.

로마자 표기(`eodigalrae`)를 쓰지 않는 이유는 영어권 가독성이 0이고 의미 전달이 안 되기 때문. 대신 §1.2 투표 질문("어디로 갈 것인가")을 그대로 옮겼다.

**네이밍 금지 규칙 (앞으로도 유지)**
- `rank` · `best` · `top` · `tier` 계열 금지 — §1.2(서열이 아니라 선호)와 충돌하고 §12.1 대학 측 리스크를 이름부터 키운다
- `odiga` · `eodiga` 계열 금지 — 교육부 대입정보포털 **'어디가'** 와 충돌. §11.2가 교차 확인 출처로 지목한 서비스라 혼동 소지가 실재한다

**미해결**: 도메인 확보, 한글명 '어디갈래'의 기존 서비스 충돌 여부 (§17 주석).

## D-008 · 계열 3분류 + SKY Program 206개 시딩

**일자** 2026-08-07 · **관련** §3, §5.4, §11.2

### 계열 7개 → 3개

```
인문 / 자연 / 예체능
```

마스터 데이터를 실제로 작성하는 과정에서 수렴한 결과다. 수험생이 실제로 쓰는 구분(문과/이과/예체능)이며, 사범계는 과목에 따라 국어교육→인문 / 수학교육→자연 / 체육교육→예체능으로 자연히 갈리고 의약계는 자연으로 들어간다. `profiles.track` 도 같은 어휘.

**D-006 이 남긴 §5.4 걱정이 이걸로 해소됐다.** 7분류일 때는 `인문` 풀이 표준 학과 4개뿐이라 매칭 쌍이 빠르게 소진될 위험이 있었는데, 3분류에서는 인문 78 · 자연 109 로 충분하다. 다만 **예체능 19개는 여전히 얇다** — §5.4 가 매칭의 90%를 동일 계열에서 뽑으므로 예체능 지망 유저는 쌍이 빨리 소진될 수 있다. 관찰 대상.

### Program 206개

| 대학 | 인문 | 자연 | 예체능 | 계 |
|---|---|---|---|---|
| 서울대 | 23 | 38 | 10 | 71 |
| 고려대(안암) | 31 | 32 | 2 | 65 |
| 연세대(신촌) | 24 | 39 | 7 | 70 |
| **합계** | **78** | **109** | **19** | **206** |

⚠️ **§11.2 공식 홈페이지 대조를 완전히 거치지 않은 데이터다.** 클로즈드 테스트용이며 오픈 베타 전 재검수가 필요하다.

### 시딩 시 내린 판단

**연세대 교차모집 7개** (응용통계·아동가족·실내건축·의류환경·식품영양·간호·통합디자인)는 원자료가 `인문/자연` 이었다. `faculty_group` 이 단일 값이고 §5.4 가 계열로 매칭 풀을 가르므로 **`자연`으로 넣었다.** 데이터이므로 UPDATE 한 줄로 바꿀 수 있다.

### 재검수 시 확인할 항목

| 항목 | 이유 |
|---|---|
| 고려대 `공과대학` | 단과대명이다. 기계공학부·전기전자공학부 등이 별도 Program 으로도 있어 "고려대 공과대학 vs 고려대 기계공학부" 매치업이 생긴다 |
| 연세대 `진리자유학부` / `진리자유학부(인문)` | 같은 학부의 계열별 모집단위가 Program 2개다. 서로 매칭될 수 있다 |
| 연세대 `언더우드학부` / `언더우드학부(인문사회)` | 위와 동일 |
| 서울대 `간호대학` | 단과대명 표기. 실제 모집단위 명칭인지 확인 |

**캠퍼스 표기**: 원자료가 `고려대(안암)` · `연세대(서울)` 였으나 `universities` 에는 캠퍼스 구분이 없다. 세종·미래 캠퍼스를 2단계에서 별도 대학으로 넣을지 결정이 필요하다.

## D-007 · 표준 학과(`majors`) 제거 — 분류는 계열까지만

**일자** 2026-08-07 · **관련** §9.1, §5.4, §4.2, §11.2

`majors` 테이블을 삭제하고 `faculty_group` 을 `programs` 로 옮겼다. **학과 단위 정규화를 하지 않는다.**

```
이전  programs (university_id, major_id → majors(name, faculty_group), display_name)
이후  programs (university_id, display_name, faculty_group)
```

### 근거

**§5.4 매칭 정책이 `major_id` 를 쓰지 않는다.** 계열로 후보를 좁히고 그 안에서 ELO 근접도와 노출 형평성으로 쌍을 고른다. §4.3 상세도 전체/계열/지역 순위만 요구하며 학과 단위 순위는 없다. 즉 `majors` 는 §4.2 "학과 검색" 하나만 지탱하고 있었다.

기획서 §9.1 은 이 매핑을 "가장 지루하고 가장 중요한 작업"이라 했고 CLAUDE.md 도 "반드시 유지"라고 못박았으나, **Program 700개를 손으로 매핑하는 비용에 상응하는 이득이 없다.** 학과 단위는 실제 명칭만으로 충분하고, 우리가 분류해 주는 것은 계열까지다.

### 부수 효과 (개선)

`faculty_group` 이 `programs` 로 내려오면서 **대학별 실제 소속을 반영할 수 있게 됐다.** `majors` 에 있을 때는 대학 무관 단일 값이라 통계학(서울대 자연과학대학 / 고려대 정경대학), 심리학, 식품영양학을 한쪽으로 몰아야 했다. D-006 이 "같이 정하자"고 남긴 항목들이 이 변경으로 사라졌다.

### 잃는 것 (인지하고 감수)

**§4.2 "학과 검색"의 정규화.** `display_name` 텍스트 검색으로는 `컴퓨터학과`·`컴퓨터공학부`는 걸려도 `소프트웨어학부`·`AI융합학부`는 '컴퓨터공학' 묶음에 걸리지 않는다. "컴퓨터공학과 중 어디가 선호되나"는 수험생이 실제로 궁금해할 질문이므로 나중에 요구가 생길 수 있다.

**되돌리는 법**: `programs.major_id` 를 **nullable** 로 추가하고 필요한 계열부터 점진적으로 매핑한다. 전량 매핑을 선행하지 않아도 되므로 지금 비용을 치를 이유가 없다.

## D-006 · Program 정체성 = 실제 학과명, 계열 7분류

**일자** 2026-08-07 · **관련** §9.1, §3, §5.4, §4.2

### 1. `UNIQUE (university_id, major_id)` → `UNIQUE (university_id, display_name)`

§9.1 의 원래 제약은 **한 대학에 표준 학과당 Program 이 하나**라는 뜻이었다. 컴퓨터공학과와 인공지능학과가 공존하는 순간 둘 중 하나를 버려야 하고, 이건 예외적 구성이 아니라 요즘 흔한 구성이다.

방향이 거꾸로였다. **실제로 존재하는 (대학, 학과)가 사실이고, 표준 분류는 그 위에 붙이는 판단이다.** 표준 학과에서 출발해 대학별 명칭을 채우는 방식은 현실이 들어갈 자리를 만들지 못한다.

- 같은 `major_id` 를 가진 Program 이 한 대학에 여럿 존재할 수 있다
- "고려대 컴퓨터학과 vs 고려대 인공지능학과" 같은 매치업도 유효해진다
- `major_id` 는 NOT NULL 유지 — 분류를 미루면 §5.4 매칭 큐에서 그 Program 이 떠버린다
- **`majors` 는 고정 시드가 아니라 자라는 목록이다.** 대학을 추가할 때마다 새 표준 학과가 생긴다

### 2. 계열 5개 → 7개

`인문사회` → `인문` / `사회`, `자연공학` → `자연` / `공학`. §3 의 정의를 바꾼다. 인문학과 사회과학, 자연과학과 공학은 지망 집단도 진로도 다르다.

`profiles.track` 도 같은 어휘로 맞췄다 — 랭킹 필터와 유저 프로필이 다른 어휘를 쓰면 §8.3 편향 분석에서 대조가 안 된다.

### ⚠️ M1 에서 결정해야 할 부작용 (§5.4)

계열이 좁아지면 **§5.4 의 "90% 동일 계열 매칭"이 좁은 풀에서 돌아간다.**

- `인문` 은 표준 학과가 4개뿐이다. 1단계(대학 3개) 기준 Program 이 12개 남짓이고, §5.6 이 (유저, 쌍)당 1회로 제한하므로 출제할 쌍이 빠르게 소진된다
- `인문` 과 `사회` 는 응시 집단이 크게 겹치는데 이제 **교차 계열(10% 버킷)** 로 밀린다. 자연↔공학도 마찬가지다

§16 #7(교차 계열 비율 10%)이 이미 미결정 항목이므로 조정은 허용 범위 안이다. **M1 에서 매칭 큐를 구현할 때 둘 중 하나를 정한다:**

1. `match.cross_faculty_rate` 를 올린다 (단순하지만 의약↔예체능 같은 무의미한 매치도 함께 늘어난다)
2. 매칭용 계열 그룹핑을 `app_config` 에 따로 둔다 — 표시·필터는 7분류, 매칭은 인문+사회 / 자연+공학을 한 풀로

2안이 §4.2.1(계열 간 점수 눈금을 잇는 것은 소수의 교차 매치)의 취지에 더 맞지만 구현이 늘어난다. **실데이터 없이 정하지 말 것.**

### 판단이 필요한 분류 (검토 요망)

대학마다 소속 단과대가 갈리는 학과를 임의로 정했다. `faculty_group` 은 `majors` 에 있고 대학 무관 단일 값이므로 하나를 골라야 한다.

| 표준 학과 | 현재 | 갈리는 이유 |
|---|---|---|
| 통계학 | `사회` | 서울대는 자연과학대학, 고려대는 정경대학 |
| 심리학 | `사회` | 대학에 따라 사회과학/자연과학 양쪽 |
| 식품영양학 | `자연` | 생활과학대학 소속이 많음 |

## D-005 · 마스터 데이터 — 단계적 확장, 계열·학교유형 제외 없음

**일자** 2026-08-07 · **관련** §11, §9.1, §4.2

### 포함 원칙 (제외하지 않는다)

| 쟁점 | 결정 |
|---|---|
| 의약 계열 | **포함.** 포함된 대학에 존재하면 넣는다 |
| 특수 이공계대(KAIST·POSTECH 등) | **포함** |
| 교대 / 초등교육 | **포함.** Program 수가 적은 건 오히려 장점 |
| `est_type` 에 `공립` 추가 | **적용** (서울시립대) |
| 서울 10 : 수도권 3 : 지방 7 분포 | **유지** |

**근거**: 계열이나 학교 유형을 이유로 제외하면 그것 자체가 사회 통념에 기반한 차별이 되고, "수험생에게 길라잡이가 된다"는 목표(§1.3)와 멀어진다. 어뷰징·항의 리스크(§12.1)는 §8 의 방어 설계로 다루는 것이지 목록에서 빼서 회피할 문제가 아니다.

이 판단은 초안(`MASTER_DATA_DRAFT.md`)이 제시한 쟁점 A·B·C 를 모두 뒤집은 것이다. 초안이 §12.1 리스크를 과대평가했다.

### 단계적 확장

클로즈드 테스트 단계에서는 20개 대학도 과하다. 단계를 나눈다.

| 단계 | 범위 | 상태 |
|---|---|---|
| **1단계 (클로즈드 테스트)** | 서울대 · 연세대 · 고려대 | `majors` 45개 + 대학 3개 시딩 완료 |
| **2단계 (오픈 베타)** | `MASTER_DATA_DRAFT.md` 의 나머지 17개 대학 + 특수 이공계대 · 교대 | 대기 |

`majors`(표준 학과 45개)는 1단계에서 **전 범위를 한 번에** 넣었다. 대학 무관 정규화 개념이라 §11.2 의 공식 홈페이지 대조 대상이 아니고, 2단계에서 대학을 추가할 때 매핑 어휘가 이미 있어야 하기 때문이다.

반면 `programs.display_name` 은 대학마다 실제 명칭이 다르므로 **반드시 공식 홈페이지 대조를 거친 뒤** 시딩한다 (§11.2). 이것이 1단계에서 대학·학과와 Program 을 분리해 넣은 이유다.

## D-004 · §5.3 연령 가중치 — 수집만 하고 적용은 보류

**일자** 2026-08-07 · **관련** §2, §5.3, §8.1, §8.6

### 배경

§2는 연령을 **카카오 로그인의 생년월일 정보**로 판정한다고 전제했다. 그러나 카카오는 생년월일·출생연도 동의항목을 **비즈 앱 전환(사업자 정보 등록) 이후에만** 허용한다. 전제가 성립하지 않는다.

### 판단의 전제

§2가 이미 인정했듯 **카카오 생년월일도 검증된 값이 아니다**("자기신고 값", "1차 방어선"). 직접 입력과의 실질적 차이는 검증 여부가 아니라 **거짓말의 비용**이다 — 카카오 값은 계정 전체에 걸려 있어 바꾸기 번거롭고 우리 가중치 체계를 알기 전에 설정된 값인 반면, 가입 폼의 입력란은 둘 다 해당하지 않는다.

특히 **§8.6이 "연령 가중치 표"를 공개하도록 명시**하므로, 자기신고 입력과 결합하면 투명성 페이지가 공략 설명서가 된다.

### 결정

**생년월일은 가입 시 직접 입력받아 수집하되, `w_age` 적용은 보류한다.** 보류 중 로그인 유저는 전원 `w_age = 1.0`.

- 스위치: `app_config` 의 **`weight.age_enabled`** (0=보류, 1=적용). 현재 **0**
- 해제 시 코드 수정 불필요 — 값만 1로 바꾸면 §5.3이 즉시 적용된다 (불변 원칙 4)
- 비로그인 투표의 `w_age = 0` 은 별개이며 `vote_submit` RPC가 처리한다

### 왜 소급 계산이 가능한가 (이 결정의 안전성 근거)

보류 구간에 쌓인 투표도 나중에 §5.3을 소급 적용할 수 있다. 별도 shadow 컬럼이 필요 없다.

| 필요한 정보 | 보존 방식 |
|---|---|
| 투표 시점의 만 나이 | `profiles.birth_date` — **수정 불가** (`grant update` 목록에 없음) + `votes.created_at` |
| 투표 시점의 `status` (N수 보정) | `profile_changes` 가 변경 이력을 타임스탬프와 함께 기록 |
| 당시 실제 적용된 가중치 | `votes.weight_applied` (§5.7) |
| 투표 원본 | `votes` append-only (불변 원칙 1) |

### 해제 조건

카카오 **비즈 앱 전환**으로 생년월일 검증이 확보되는 시점. **§8.6 공개 페이지(M3) 전까지 완료하는 것을 목표로 한다** — 공개 페이지가 열리기 전이라 아직 공략할 정보가 노출되어 있지 않다.

전환 후에는 카카오 생년월일과 직접 입력값을 대조해, 불일치 계정의 `c_trust`를 §8.3의 기존 감쇠 메커니즘으로 낮춘다. §8.3 원칙대로 **이미 반영된 과거 투표는 소급 조정하지 않는다.**

### 부록 · 비즈 앱 게이트는 이메일에도 걸린다 (2026-08-07 확인)

구현 중 확인된 사실. 카카오 `account_email` 동의항목도 **비즈 앱 전용**이다. 생년월일과 같은 게이트다.

Supabase Kakao provider 는 기본으로 `account_email profile_image profile_nickname` 을 요청하는데, 앱에 설정되지 않은 동의항목이 섞이면 카카오가 **KOE205** 로 거절한다.

**클라이언트 코드로는 못 고친다.** `signInWithOAuth({ options: { scopes } })` 는 기본 scope 를 **대체하지 않고 덧붙인다** — 실측 결과:

```
scopes 미지정            → account_email profile_image profile_nickname
scopes=profile_nickname  → account_email profile_image profile_nickname profile_nickname
```

**Supabase 대시보드의 `Allow users without an email` 로도 해결되지 않는다.** 그 설정은 이메일 없는 유저를 *받아들이는* 것이지 요청 scope 를 바꾸지 않는다 — 켠 뒤에도 scope 는 그대로였다(3회 실측). Supabase Kakao provider 는 `account_email` 을 고정으로 요청하며 이를 빼는 수단이 없다.

### 결정: 비즈 앱 전환으로 해결한다 (2026-08-07)

전환 하나로 두 가지가 동시에 풀리기 때문이다.

| | 해결 방법 |
|---|---|
| 로그인 (KOE205) | `account_email` 동의항목 활성화 → **코드 변경 없음** |
| 연령 가중치 (D-004) | `signInWithOAuth({ options: { scopes: 'birthday birthyear' } })` **한 줄** |

두 번째가 가능한 이유가 위에서 확인한 "scopes 는 추가된다"는 성질이다. 제거는 못 해도 **추가는 되므로**, 비즈 앱에서 동의항목만 열리면 생년월일을 받아올 수 있다.

전환 전까지 로그인이 동작하지 않으므로 **M0 완료가 여기에 묶여 있다.**

### 기각한 대안 · OIDC 직접 연동

`signInWithIdToken` 으로 카카오 OIDC 를 직접 물면 비즈 앱 없이도 로그인이 되고 scope 통제권도 얻는다(`profile_image` 강제 수집을 피할 수 있어 §12.2 에 부합). 그러나 OAuth `state` 검증(CSRF 방어)을 직접 구현해야 해 보안에 직결되는 코드가 늘고, 비즈 앱 전환은 D-004 때문에 어차피 해야 한다. 전환이 막히면 이 안으로 되돌아온다.

`auth.users.email` 은 전환 전까지 비어 있다. 이메일을 쓰는 기능(알림 등 §10.5 `P2`)을 설계할 때 확인할 것.

### 기각한 대안

- **로직 비공개** — §8.6과 정면 충돌. 그 공개 페이지는 §12.1 대학 측 항의에 대한 방어 카드("자의적 조작이 없음을 보이는 근거")이기도 하다. 은닉은 리버스 엔지니어링으로 무력화된다
- **직접 입력 후 즉시 적용** — 위 공략 설명서 문제. 다만 비즈 앱 전환이 지연되면 재검토 대상
