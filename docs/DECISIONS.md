## D-001 · 서비스 영문명 `whereto`

**일자** 2026-08-07 · **관련** §17

한글명 **어디갈래** 확정(§17 후보 중), 영문명·코드 슬러그는 **`whereto`**. 저장소·패키지·도메인 전부 동일.

로마자 표기(`eodigalrae`)를 쓰지 않는 이유는 영어권 가독성이 0이고 의미 전달이 안 되기 때문. 대신 §1.2 투표 질문("어디로 갈 것인가")을 그대로 옮겼다.

**네이밍 금지 규칙 (앞으로도 유지)**
- `rank` · `best` · `top` · `tier` 계열 금지 — §1.2(서열이 아니라 선호)와 충돌하고 §12.1 대학 측 리스크를 이름부터 키운다
- `odiga` · `eodiga` 계열 금지 — 교육부 대입정보포털 **'어디가'** 와 충돌. §11.2가 교차 확인 출처로 지목한 서비스라 혼동 소지가 실재한다

**미해결**: 도메인 확보, 한글명 '어디갈래'의 기존 서비스 충돌 여부 (§17 주석).

## D-013 · 매치업 품질 피드백 루프 + 공개 점검 시점

**일자** 2026-08-08 · **관련** §5.4, §7.2, §4.2.1, §12.2

### 1. 공개 점검은 M4 직전에 한 번에

현재는 클로즈드 단계로 본다. 약관·개인정보처리방침 초안은 작성했으나(§12.2), **`legal/constants.ts` 의 `[[ ]]` 를 채우는 것과 법률 검토는 M4 직전 본격 공개 점검 때 일괄 처리한다.** 그때 함께 볼 항목:

- `legal/constants.ts` 실제 값 기입, 법률 검토
- 카카오 로그인 심사 제출
- §1.5 "만든 이유" · §8.6 "산출 방식" 공개 페이지 (약관 제7조 4항이 산출 방식 공개를 약속했다)
- 마스터 데이터 §11.2 공식 홈페이지 재대조 (D-008 의 미검증 데이터)

### 2. 스킵률을 관찰이 아니라 알고리즘으로 반영한다

D-009·D-011 은 "스킵률을 보고 교차 비율을 재조정한다"고 남겼다. **관찰 도구가 아니라 피드백 루프로 만든다** — 사람이 보고 손으로 고치는 방식은 조합이 늘수록 확장되지 않는다.

**목표**: 좋은 평가를 받은 매치업 유형을 더 자주 띄운다.

**신호** (전부 수집 시작함):

| 신호 | 의미 | 상태 |
|---|---|---|
| `skips` | 부정 — 답하기 어려웠다 | 수집 중 |
| `votes` | 긍정 — 답할 수 있었다 | 수집 중 |
| `matchup_feedback` | 명시적 👍/👎 | **이번에 추가** |
| `votes.response_ms` | 보조 — 고민 시간 | 수집 중 |

집계 단위는 **개별 쌍이 아니라 매치업 유형**이다. §5.6 이 (유저, 쌍)당 1회로 제한해 개별 쌍은 표본이 극히 얇다. 계열 조합 × ELO 격차 구간이 실질적인 단위다. 관찰 창구로 `matchup_quality_by_faculty` 뷰를 만들어 뒀다(어드민 전용).

### ⚠️ 설계 시 반드시 걸 안전장치

**"답하기 쉬운 매치를 늘린다"는 §5.4 의 "정보량이 큰 매치를 띄운다"와 충돌한다.**

- ELO 근접 쌍은 정보량이 최대인 동시에 **가장 고민되는(=스킵되기 쉬운)** 쌍이다. 스킵률만 보고 줄이면 지수가 정보를 잃는다
- 교차 계열도 스킵률이 높을 것이나, 줄이면 §4.2.1 이 지적한 계열 간 눈금이 더 끊긴다

**기획서가 §7.2 에서 같은 문제를 이미 풀었다** — 평판이 가중치를 크게 좌우하면 다수 동조 되먹임이 생기니 ±15% 로 묶는다는 논리. 매치업 품질도 같은 형태로 간다:

1. 품질 계수의 **영향 폭을 제한**한다 (§7.2 처럼 clamp)
2. 조합별 **최소 노출 비율을 보장**한다 — 특히 교차 계열은 §4.2.1 때문에 0 이 되면 안 된다
3. 계수는 `app_config` 로 외부화한다 (불변 원칙 4)

**구현 시점**: 데이터가 쌓인 뒤. §8.3 편향 탐지 배치와 같은 성격(배치 산출 품질 신호)이라 **M3 에 함께 넣는다.** 지금은 수집만 한다 — 알고리즘은 나중에 만들 수 있지만 데이터는 소급해서 만들 수 없다.

## D-012 · 랭킹을 행 테이블이 아니라 배치표로

**일자** 2026-08-07 · **관련** §4.2, §14.1, §14.3, §16 #3

### 형태

세로축이 **선호도 지수**, 대학이 **컬럼**, 각 학과가 자기 지수 높이에 라벨로 찍힌다. 수험생이 실제로 쓰는 배치표 형식이다.

§4.2 는 `순위 / 변동 / 대학 / 학과 / 지수 / 배지 / 표본 / 승률` 컬럼의 행 테이블을 규정하고 §14.3 은 "랭킹표는 표처럼 보여야 한다"고 했다. 배치표는 행 테이블이 아니므로 **문자상으로는 위반**이다.

그럼에도 채택한 이유: §14.1 이 오르비의 "입결표 UI 문법"을 차용하라고 했고, 수험생이 실제로 쓰는 것이 배치표다. **문자보다 의도에 충실한 선택**이라고 판단했다.

**잃는 것**: 순위 번호·변동(▲▼)·표본 수·승률이 한눈에 보이지 않는다. → 라벨을 탭/클릭하면 뜨는 하단 상세 패널로 옮겼다.

### 대학이 늘어날 때 — 컬럼 패킹

**세로축은 하나만 쓴다.** 대학을 컬럼에 배치하되, 앞 대학의 최하위 학과가 끝난 지점 아래면 **같은 컬럼을 재사용**한다.

세로축을 대학마다 반복하면 "같은 높이 = 같은 지수" 관계가 끊어져 배치표가 성립하지 않는다. 패킹은 그 관계를 지키면서 가로 폭을 아낀다 — 실제 배치표가 이 구조다.

현재는 202개가 전부 1500 이라 세 대학 구간이 완전히 겹쳐 3컬럼으로 나온다. 지수가 벌어지면 패킹이 자동으로 작동한다.

### 같은 지수 겹침 처리

이상 위치(`(maxElo - elo) × 3px`)에 두되, 겹치면 아래로 밀어낸다. 지수가 전부 같은 현재 상태에서는 자연히 조밀한 세로 목록으로 degrade 한다.

### 예체능 제외

D-011 로 예체능이 별도 리그가 되어 지수 척도가 인문·자연과 이어지지 않는다. **조회에서 제외한다** — 데이터는 그대로 두고 화면에만 안 나온다. 나중에 별도 탭으로 되살릴 수 있다.

### §16 #3 결정 — 고지 문구는 하단

§12.1 대학 측 리스크 고지 문구의 배치가 §16 #3 미결정이었다. **하단으로 확정한다.** 상단에 두면 배치표의 시각적 밀도를 해친다. §4.2.1 계열 간 비교 안내도 함께 하단에 상시 노출한다.

### ISR 을 위한 별도 클라이언트

`server.ts` 의 Supabase 클라이언트는 `cookies()` 를 읽어 라우트를 동적으로 만든다. §13.3 의 `revalidate: 600` 을 살리기 위해 쿠키를 건드리지 않는 `createPublicClient()` 를 따로 뒀다. 빌드 출력에서 `/ranking` 이 `Revalidate 10m` 정적 라우트로 잡히는 것으로 확인했다.

## D-011 · 예체능 매칭 분리 — §5.4 "유저 계열 미반영" 원칙의 예외

**일자** 2026-08-07 · **관련** §5.4, §4.2.1, §16 #7

### 정책

| 상황 | 예체능 등장 | 예체능↔비예체능 |
|---|---|---|
| 일반 유저 | 7% (`match.arts_rate_default`) | 7% (`match.arts_cross_rate`) |
| `track = 예체능` 유저 | 90% (`match.arts_rate_arts_user`) | 7% |

예체능이 등장하지 않는 매치업은 인문/자연 풀에서 §5.4 의 동일/교차 규칙(현재 교차 50%, D-009)을 그대로 적용한다.

**실측 분포** (600회 샘플):

| | 일반 유저 | 예체능 유저 |
|---|---|---|
| 인문↔인문 / 자연↔자연 / 인문↔자연 | 20 / 26 / 47% | 3 / 2 / 5% |
| 예체능↔예체능 | 7% | 84% |
| 예체능↔비예체능 | 1% | 7% |

### ⚠️ §5.4 와 정면 충돌한다

기획서는 이렇게 못박았다:

> 유저 프로필 계열을 매칭에 반영하면 응답 품질은 오르나 데이터가 편중된다. **초기에는 반영하지 않고**, 데이터 축적 후 A/B로 검증한다.

이 결정은 `profiles.track` 을 매칭에 반영한다. 그럼에도 진행하는 이유: 음대 지망이 아닌 유저에게 "성악과 vs 기악과"를 묻는 것은 응답이 아니라 노이즈다. 스킵률만 올리고 지수 품질에 기여하지 않는다.

### 대가 — 예체능은 사실상 별도 리그가 된다

예체능 Program 의 지수는 **예체능 유저들만의 척도**가 된다. 인문/자연과 연결하는 표는 전체의 1~7% 뿐이라 계열 간 눈금이 거의 이어지지 않는다.

따라서:

- **전체 랭킹에서 예체능 Program 의 위치는 신뢰도가 낮다.** §4.2.1 의 계열 간 비교 안내 문구가 예체능에 대해서는 더 강하게 적용되어야 한다
- 랭킹 화면에서 예체능을 기본 노출에서 분리하거나 별도 표기하는 것을 검토해야 한다
- `track` 은 유저가 변경할 수 있고 `profile_changes` 에 기록된다. 예체능 노출을 노린 track 변경이 어뷰징 신호가 될 수 있다 (§8.3 배치에서 관찰)

### 백로그 (장기)

- **매치업 자체에 대한 좋아요/싫어요** — 화면 우상단 작은 버튼. 매칭 품질 피드백을 직접 수집한다. 현재는 `skips` 가 유일한 품질 신호다
- **레이팅 근접 매칭 강화** — 이미 §5.4 의 `match.close_pair_rate`(70%)로 구현돼 있다. 지금은 콜드스타트 구간이라 `coldstart_close_rate`(30%)가 적용 중이며, 누적 투표 5,000 도달 시 자동으로 70%로 올라간다. 추가 구현 불필요

## D-010 · 투표 화면 — 모바일도 좌우 분할, 카드 색은 중립 유지

**일자** 2026-08-07 · **관련** §14.2, §14.4, §4.1, §4.1.1

### 1. 모바일도 좌우 분할 (§14.2 변경)

§14.2 는 모바일을 "카드 상하 분할, 엄지 도달 범위에 선택 영역"으로 규정했으나 **좌우 분할로 통일한다.**

비교는 나란히 놓을 때 가장 잘 되고, 상하 분할은 "대결"이 아니라 "목록"처럼 읽힌다. 엄지 도달 범위는 카드 전체를 탭 영역으로 두어 하단만 눌러도 되게 해결했다.

**대가**: 375px 에서 카드 폭 172px, 안쪽 148px 이다. 한글 단어 중간이 끊기지 않도록 `break-keep` 을 쓰고 폰트를 반응형(`text-xl` → `lg:text-3xl`)으로 잡았다.

배포본 375px 에서 실측한 결과 현재 데이터는 전부 들어간다:

| 학과명 | 폭 |
|---|---|
| 융합인문사회과학부(HASS) | 141px |
| 바이오시스템·소재학부 | 114px |
| 조경지역시스템공학부 | 111px |
| (안쪽 여유) | **148px** |

⚠️ **가장 긴 이름의 여유가 7px 뿐이다.** 2단계 확장에서 더 긴 학과명이 들어오면 넘친다. 대학 추가 시 375px 에서 재측정할 것.

### 2. 대학별 테마 색 — 도입하지 않음 (장기 검토 보류)

카드에 대학 상징색을 입히자는 제안이 있었으나 **현재는 도입하지 않는다.** 판단에 필요한 근거를 남긴다.

§14.4 는 "좌/우를 파랑 vs 빨강 등으로 칠하면 특정 학교 상징색을 **연상시켜** 선택에 영향을 준다"고 경고한다. 실제 학교 색을 쓰는 것은 이 우려의 완화판이 아니라 **강화판**이다. 고려대 크림슨 vs 연세대 블루는 §1.3 이 지목한 "훌리건 문화"의 시각적 트리거 그 자체다.

**더 중요한 것: §8.3 편향 탐지로 잡을 수 없는 종류의 왜곡이다.** 어뷰징 탐지는 비정상 계정을 골라내지만, 색으로 유도된 편향은 모든 유저에게 고르게 작용해 통계적으로 정상처럼 보인다. 탐지 자체가 성립하지 않는다.

**다만 선은 로고에 있지 않다.** §4.1 이 카드에 대학 로고를 넣도록 이미 명시하므로 브랜드 식별은 어차피 들어간다. 장기 검토 시 경계는 여기로 본다:

- 허용 가능: 로고 옆 작은 색 점, 얇은 스트라이프 — **식별 보조**
- 위험: 카드 배경·테두리 전체를 학교 색으로 — **정서적 프레이밍**

### 3. `votes.reason` 쓰기 1회 허용 (§4.1 ↔ §4.1.1 충돌 해소)

§4.1 은 "카드 선택 → **즉시 확정**", §4.1.1 은 "**투표 직후** 선택적으로 이유 입력"이다. 그런데 `votes` 가 append-only 라 `reason` 을 나중에 채울 수 없었다.

`reason` 을 **쓰기 1회**로 열었다. `NULL → 값` 은 허용, `값 → 다른 값` 은 트리거가 막는다. 투표 내용(선택·가중치·ELO)은 여전히 불변이다 — 이유는 투표가 아니라 투표에 덧붙는 논거다.

한번 쓴 논거를 고쳐 쓸 수 없게 한 이유: §7 평판이 공개된 이유를 평가 대상으로 삼으므로, 추천을 받은 뒤 내용을 바꾸면 평가가 사후에 무의미해진다.

`vote_add_reason(vote_id, reason, public)` RPC 로 노출한다.

| 고려대 `공과대학` | 단과대명. 기계공학부·전기전자공학부가 별도 Program 이라 포함관계 매치업이 생긴다 |
| 연세대 `진리자유학부` · `진리자유학부(인문)` · `언더우드학부(인문사회)` | 같은 학부의 계열별 모집단위가 Program 4개였다. `언더우드학부`(인문) 하나만 남겼다 |

서울대 `간호대학`은 유지 — 실제 모집단위 표기다.

최종: 서울대(관악) 71 · 연세대(신촌) 67 · 고려대(안암) 64 = **202**. 인문 77 · 자연 106 · 예체능 19.

### 캠퍼스 구분 도입

`universities.campus` 추가, `UNIQUE (name)` → `UNIQUE (name, campus)`. 현재 값은 관악 / 신촌 / 안암.

지방 캠퍼스(고려대 세종, 연세대 미래) 추가 여부는 **미정**이다. 다만 구분을 지금 넣어두면 나중에 `고려대학교(세종)` 같은 이름 꼼수를 쓰지 않아도 된다. 표시에는 캠퍼스가 둘 이상일 때만 쓴다.

### 교차 계열 비율 10% → 50% (§16 #7 결정)

**문이과 통합이 추세이므로 인문↔자연 비교의 의미가 커졌다**는 판단. 계열 간 점수 눈금을 잇는 교차 매치가 늘어나 §4.2.1 이 지적한 구조적 한계도 완화된다.

**⚠️ 관찰 필요**: 3분류에서 교차는 인문↔자연뿐 아니라 `X↔예체능`도 포함한다. "서울대 성악과 vs 연세대 의예과" 같은 쌍은 §1.2 질문("둘 다 갈 수 있다면")에 답하기 어려워 스킵률이 오를 수 있다. 문이과 통합 논거는 예체능에는 적용되지 않는다.

M1 에서 `skips` 테이블로 **계열 조합별 스킵률**을 집계해 재조정한다. 필요하면 교차 비율을 조합별로 분리한다(인문↔자연은 높게, X↔예체능은 낮게).

## D-007 · 표준 학과(`majors`) 제거 — 분류는 계열까지만

**일자** 2026-08-07 · **관련** §9.1, §5.4, §4.2, §11.2

`majors` 테이블을 삭제하고 `faculty_group` 을 `programs` 로 옮겼다. **학과 단위 정규화를 하지 않는다.**

```
이전  programs (university_id, major_id → majors(name, faculty_group), display_name)
이후  programs (university_id, display_name, faculty_group)
```

### 근거

**§5.4 매칭 정책이 `major_id` 를 쓰지 않는다.** 계열로 후보를 좁히고 그 안에서 ELO 근접도와 노출 형평성으로 쌍을 고른다. §4.3 상세도 전체/계열/지역 순위만 요구하며 학과 단위 순위는 없다. 즉 `majors` 는 §4.2 "학과 검색" 하나만 지탱하고 있었다.

기획서 §9.1 은 이 매핑을 "가장 지루하고 가장 중요한 작업"이라 했고 CLAUDE.md 도 "반드시 유지"라고 못박았으나, **Program 700개를 손으로 매핑하는 비용에 상응하는 이득이 없다.** 학과 단위는 실제 명칭만으로 충분하고, 우리가 분류해 주는 것은 계열까지다.

### 부수 효과 (개선)

`faculty_group` 이 `programs` 로 내려오면서 **대학별 실제 소속을 반영할 수 있게 됐다.** `majors` 에 있을 때는 대학 무관 단일 값이라 통계학(서울대 자연과학대학 / 고려대 정경대학), 심리학, 식품영양학을 한쪽으로 몰아야 했다. D-006 이 "같이 정하자"고 남긴 항목들이 이 변경으로 사라졌다.

### 잃는 것 (인지하고 감수)

**§4.2 "학과 검색"의 정규화.** `display_name` 텍스트 검색으로는 `컴퓨터학과`·`컴퓨터공학부`는 걸려도 `소프트웨어학부`·`AI융합학부`는 '컴퓨터공학' 묶음에 걸리지 않는다. "컴퓨터공학과 중 어디가 선호되나"는 수험생이 실제로 궁금해할 질문이므로 나중에 요구가 생길 수 있다.

**되돌리는 법**: `programs.major_id` 를 **nullable** 로 추가하고 필요한 계열부터 점진적으로 매핑한다. 전량 매핑을 선행하지 않아도 되므로 지금 비용을 치를 이유가 없다.

## D-006 · Program 정체성 = 실제 학과명, 계열 7분류

**일자** 2026-08-07 · **관련** §9.1, §3, §5.4, §4.2

### 1. `UNIQUE (university_id, major_id)` → `UNIQUE (university_id, display_name)`

§9.1 의 원래 제약은 **한 대학에 표준 학과당 Program 이 하나**라는 뜻이었다. 컴퓨터공학과와 인공지능학과가 공존하는 순간 둘 중 하나를 버려야 하고, 이건 예외적 구성이 아니라 요즘 흔한 구성이다.

방향이 거꾸로였다. **실제로 존재하는 (대학, 학과)가 사실이고, 표준 분류는 그 위에 붙이는 판단이다.** 표준 학과에서 출발해 대학별 명칭을 채우는 방식은 현실이 들어갈 자리를 만들지 못한다.

- 같은 `major_id` 를 가진 Program 이 한 대학에 여럿 존재할 수 있다
- "고려대 컴퓨터학과 vs 고려대 인공지능학과" 같은 매치업도 유효해진다
- `major_id` 는 NOT NULL 유지 — 분류를 미루면 §5.4 매칭 큐에서 그 Program 이 떠버린다
- **`majors` 는 고정 시드가 아니라 자라는 목록이다.** 대학을 추가할 때마다 새 표준 학과가 생긴다

### 2. 계열 5개 → 7개

`인문사회` → `인문` / `사회`, `자연공학` → `자연` / `공학`. §3 의 정의를 바꾼다. 인문학과 사회과학, 자연과학과 공학은 지망 집단도 진로도 다르다.

`profiles.track` 도 같은 어휘로 맞췄다 — 랭킹 필터와 유저 프로필이 다른 어휘를 쓰면 §8.3 편향 분석에서 대조가 안 된다.

### ⚠️ M1 에서 결정해야 할 부작용 (§5.4)

계열이 좁아지면 **§5.4 의 "90% 동일 계열 매칭"이 좁은 풀에서 돌아간다.**

- `인문` 은 표준 학과가 4개뿐이다. 1단계(대학 3개) 기준 Program 이 12개 남짓이고, §5.6 이 (유저, 쌍)당 1회로 제한하므로 출제할 쌍이 빠르게 소진된다
- `인문` 과 `사회` 는 응시 집단이 크게 겹치는데 이제 **교차 계열(10% 버킷)** 로 밀린다. 자연↔공학도 마찬가지다

§16 #7(교차 계열 비율 10%)이 이미 미결정 항목이므로 조정은 허용 범위 안이다. **M1 에서 매칭 큐를 구현할 때 둘 중 하나를 정한다:**

1. `match.cross_faculty_rate` 를 올린다 (단순하지만 의약↔예체능 같은 무의미한 매치도 함께 늘어난다)
2. 매칭용 계열 그룹핑을 `app_config` 에 따로 둔다 — 표시·필터는 7분류, 매칭은 인문+사회 / 자연+공학을 한 풀로

2안이 §4.2.1(계열 간 점수 눈금을 잇는 것은 소수의 교차 매치)의 취지에 더 맞지만 구현이 늘어난다. **실데이터 없이 정하지 말 것.**

### 판단이 필요한 분류 (검토 요망)

대학마다 소속 단과대가 갈리는 학과를 임의로 정했다. `faculty_group` 은 `majors` 에 있고 대학 무관 단일 값이므로 하나를 골라야 한다.

| 표준 학과 | 현재 | 갈리는 이유 |
|---|---|---|
| 통계학 | `사회` | 서울대는 자연과학대학, 고려대는 정경대학 |
| 심리학 | `사회` | 대학에 따라 사회과학/자연과학 양쪽 |
| 식품영양학 | `자연` | 생활과학대학 소속이 많음 |

## D-005 · 마스터 데이터 — 단계적 확장, 계열·학교유형 제외 없음

클로즈드 테스트 단계에서는 20개 대학도 과하다. 단계를 나눈다.

| 단계 | 범위 | 상태 |
|---|---|---|
| **1단계 (클로즈드 테스트)** | 서울대 · 연세대 · 고려대 | `majors` 45개 + 대학 3개 시딩 완료 |

## D-004 · §5.3 연령 가중치 — 수집만 하고 적용은 보류

**일자** 2026-08-07 · **관련** §2, §5.3, §8.1, §8.6

### 배경

§2는 연령을 **카카오 로그인의 생년월일 정보**로 판정한다고 전제했다. 그러나 카카오는 생년월일·출생연도 동의항목을 **비즈 앱 전환(사업자 정보 등록) 이후에만** 허용한다. 전제가 성립하지 않는다.

### 판단의 전제

§2가 이미 인정했듯 **카카오 생년월일도 검증된 값이 아니다**("자기신고 값", "1차 방어선"). 직접 입력과의 실질적 차이는 검증 여부가 아니라 **거짓말의 비용**이다 — 카카오 값은 계정 전체에 걸려 있어 바꾸기 번거롭고 우리 가중치 체계를 알기 전에 설정된 값인 반면, 가입 폼의 입력란은 둘 다 해당하지 않는다.

특히 **§8.6이 "연령 가중치 표"를 공개하도록 명시**하므로, 자기신고 입력과 결합하면 투명성 페이지가 공략 설명서가 된다.

### 결정

**생년월일은 가입 시 직접 입력받아 수집하되, `w_age` 적용은 보류한다.** 보류 중 로그인 유저는 전원 `w_age = 1.0`.

- 스위치: `app_config` 의 **`weight.age_enabled`** (0=보류, 1=적용). 현재 **0**
- 해제 시 코드 수정 불필요 — 값만 1로 바꾸면 §5.3이 즉시 적용된다 (불변 원칙 4)
- 비로그인 투표의 `w_age = 0` 은 별개이며 `vote_submit` RPC가 처리한다

### 왜 소급 계산이 가능한가 (이 결정의 안전성 근거)

보류 구간에 쌓인 투표도 나중에 §5.3을 소급 적용할 수 있다. 별도 shadow 컬럼이 필요 없다.

| 필요한 정보 | 보존 방식 |
|---|---|
| 투표 시점의 만 나이 | `profiles.birth_date` — **수정 불가** (`grant update` 목록에 없음) + `votes.created_at` |
| 투표 시점의 `status` (N수 보정) | `profile_changes` 가 변경 이력을 타임스탬프와 함께 기록 |
| 당시 실제 적용된 가중치 | `votes.weight_applied` (§5.7) |
| 투표 원본 | `votes` append-only (불변 원칙 1) |

### 해제 조건

카카오 **비즈 앱 전환**으로 생년월일 검증이 확보되는 시점. **§8.6 공개 페이지(M3) 전까지 완료하는 것을 목표로 한다** — 공개 페이지가 열리기 전이라 아직 공략할 정보가 노출되어 있지 않다.

전환 후에는 카카오 생년월일과 직접 입력값을 대조해, 불일치 계정의 `c_trust`를 §8.3의 기존 감쇠 메커니즘으로 낮춘다. §8.3 원칙대로 **이미 반영된 과거 투표는 소급 조정하지 않는다.**

### 부록 · 비즈 앱 게이트는 이메일에도 걸린다 (2026-08-07 확인)

구현 중 확인된 사실. 카카오 `account_email` 동의항목도 **비즈 앱 전용**이다. 생년월일과 같은 게이트다.

Supabase Kakao provider 는 기본으로 `account_email profile_image profile_nickname` 을 요청하는데, 앱에 설정되지 않은 동의항목이 섞이면 카카오가 **KOE205** 로 거절한다.

**클라이언트 코드로는 못 고친다.** `signInWithOAuth({ options: { scopes } })` 는 기본 scope 를 **대체하지 않고 덧붙인다** — 실측 결과:

```
scopes 미지정            → account_email profile_image profile_nickname
scopes=profile_nickname  → account_email profile_image profile_nickname profile_nickname
```

**Supabase 대시보드의 `Allow users without an email` 로도 해결되지 않는다.** 그 설정은 이메일 없는 유저를 *받아들이는* 것이지 요청 scope 를 바꾸지 않는다 — 켠 뒤에도 scope 는 그대로였다(3회 실측). Supabase Kakao provider 는 `account_email` 을 고정으로 요청하며 이를 빼는 수단이 없다.

### 결정: 비즈 앱 전환으로 해결한다 (2026-08-07)

전환 하나로 두 가지가 동시에 풀리기 때문이다.

| | 해결 방법 |
|---|---|
| 로그인 (KOE205) | `account_email` 동의항목 활성화 → **코드 변경 없음** |
| 연령 가중치 (D-004) | `signInWithOAuth({ options: { scopes: 'birthday birthyear' } })` **한 줄** |

두 번째가 가능한 이유가 위에서 확인한 "scopes 는 추가된다"는 성질이다. 제거는 못 해도 **추가는 되므로**, 비즈 앱에서 동의항목만 열리면 생년월일을 받아올 수 있다.

전환 전까지 로그인이 동작하지 않으므로 **M0 완료가 여기에 묶여 있다.**

### 기각한 대안 · OIDC 직접 연동

`signInWithIdToken` 으로 카카오 OIDC 를 직접 물면 비즈 앱 없이도 로그인이 되고 scope 통제권도 얻는다(`profile_image` 강제 수집을 피할 수 있어 §12.2 에 부합). 그러나 OAuth `state` 검증(CSRF 방어)을 직접 구현해야 해 보안에 직결되는 코드가 늘고, 비즈 앱 전환은 D-004 때문에 어차피 해야 한다. 전환이 막히면 이 안으로 되돌아온다.

`auth.users.email` 은 전환 전까지 비어 있다. 이메일을 쓰는 기능(알림 등 §10.5 `P2`)을 설계할 때 확인할 것.

### 기각한 대안

- **로직 비공개** — §8.6과 정면 충돌. 그 공개 페이지는 §12.1 대학 측 항의에 대한 방어 카드("자의적 조작이 없음을 보이는 근거")이기도 하다. 은닉은 리버스 엔지니어링으로 무력화된다
- **직접 입력 후 즉시 적용** — 위 공략 설명서 문제. 다만 비즈 앱 전환이 지연되면 재검토 대상
